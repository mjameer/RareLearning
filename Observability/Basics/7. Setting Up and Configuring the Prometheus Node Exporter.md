This text provides a detailed, step-by-step tutorial on setting up and configuring the **Prometheus Node Exporter** to collect machine metrics from a Linux (or Unix-based) server.

The summary covers the following key points:

### Node Exporter Overview
* The **Node Exporter** is an official Prometheus tool used for collecting kernel-level metrics (such as CPU, memory, and disk usage) from **Unix-based systems** (referred to as "nodes").
* The name is clarified, noting that "node" in this context refers to a kernel-based server, and has **nothing to do with Node.js**.
* The Exporter is installed on the **application server** whose metrics are needed, not typically on the Prometheus server itself.

### Essential Security and Installation
* **Firewall Configuration:** The application server's firewall must be configured to open **port 9100**, which is the port the Node Exporter uses to expose metrics.
* **Best Practice Security:** Critically, access to port 9100 must be restricted so that **only the Prometheus server** (using its specific IP address or security group ID) can scrape the metrics, preventing unauthorized access.
* **Installation:** The process involves downloading the Node Exporter package from the Prometheus website, extracting it, and running the `node_exporter` executable on the application server.

### Configuring Prometheus to Scrape Metrics
* The **Prometheus configuration file** (`prometheus.yml` or `.yml`) must be updated with a new `scrape_config` job.
* This job is given a name (e.g., "application\_server") and points to the private IP address of the application server at port 9100.
* **Restarting Prometheus:** After modifying the YAML configuration, the Prometheus service must be restarted (`sudo systemctl stop/start prometheus`) to apply the changes.
* **Verification:** Once restarted, the Prometheus UI's **Targets** page is used to confirm that the new target is successfully being scraped (shown as **"UP"**), indicating a successful setup.

### Self-Monitoring
* It is noted that Prometheus is capable of **monitoring its own metrics** because it has an internal exporter, which is configured by default under the `job_name: prometheus` in the config file.
